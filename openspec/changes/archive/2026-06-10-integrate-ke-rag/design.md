## Context

Milo-V2 是基于 AgentScope 的 AI Agent 对话平台，后端由 `create_app` 自动生成路由，前端通过 SSE 接收 Agent 事件流。当前对话流程为：用户输入 → Agent（ReAct 循环） → LLM 生成回答 → 前端渲染。

ke-rag 是贝壳内部的知识检索增强服务，提供文件解析、知识索引、多路召回等能力。项目中已有 ke-rag 的接口规范文档（`.claude/skills/ke-rag/SKILL.md`），但尚未集成。

nrs-agent（SRE-Agent）已有完整的 RAG 检索引用实现，采用"查询改写 → 混合检索 → 重排序 → 上下文注入 → LLM 引用"的流程，可作为参考。

## Goals / Non-Goals

**Goals:**
- 在 Agent 对话前自动检索知识库，将结果作为上下文注入
- LLM 回答中引用知识库来源，前端渲染引用卡片
- 知识库检索层具备抽象性，支持后续替换数据源或检索逻辑
- 支持配置检索模式（fast/normal/ultra）和返回条数

**Non-Goals:**
- 不实现文件上传和索引管理（使用已有知识库）
- 不实现 Rerank 重排序（依赖 ke-rag 服务端能力）
- 不实现查询改写（首期使用原始查询，后续可扩展）
- 不实现 DeepRAG 模式（首期仅使用 search 接口）

## Decisions

### D1: RAG 作为 Tool 还是中间件

**选择：作为 Tool（Agent 可调用的工具）**

理由：
- AgentScope 框架的 Agent 运行时由框架控制，项目代码无法直接插入中间件
- 通过注册 Tool，Agent 可以自主决定何时检索知识库，更灵活
- 符合 AgentScope 的 Tool Calling 机制，与现有 Bash/Read/Write 等工具一致

替代方案：
- 修改 AgentScope 源码注入中间件 → 侵入性太强，维护成本高
- 在 system prompt 中固定注入检索指令 → Agent 无法自主控制检索时机

### D2: 知识检索接口选择

**选择：使用 `/v1/rag/search` 接口**

理由：
- search 接口返回原始检索结果，我们可以自行格式化和注入上下文
- chat 接口会直接生成回答，绕过了我们自己的 LLM，失去控制权
- search 结果更灵活，支持自定义引用格式

### D3: 引用格式设计

**选择：Markdown 内联引用 + 独立引用区块**

参考 nrs-agent 的实现，采用以下格式：

```markdown
[引用1] 根据知识库内容，...

---
**引用来源：**
1. 文件名 - 标题 [查看原文](/api/knowledge/chunks/{id})
```

理由：
- 内联引用让回答更流畅
- 独立引用区块便于用户快速定位来源
- 与 nrs-agent 的实现保持一致

### D4: 检索结果缓存策略

**选择：不缓存（首期）**

理由：
- ke-rag 服务端已有缓存机制
- 首期优先保证功能正确性，性能优化后续迭代
- 知识库内容可能更新，缓存可能导致数据不一致

### D5: 配置管理

**选择：环境变量 + Agent 配置**

- 全局配置：API Key、Base URL（环境变量）
- Agent 级配置：Space ID、检索模式、返回条数（Agent 配置）
- 运行时配置：用户 ID（从请求 header 获取）

## Risks / Trade-offs

- **[延迟增加]** 知识检索会增加 200-500ms 响应时间 → 使用 `fast` 模式作为默认，仅在需要高精度时切换 `normal`/`ultra`
- **[Agent 自主性]** Agent 可能不总是调用知识检索工具 → 在 system prompt 中添加引导指令，建议在知识相关问题时使用
- **[引用准确性]** LLM 可能生成不准确的引用 → 在 prompt 中明确引用格式要求，添加负向约束
- **[ke-rag 服务可用性]** 外部服务可能不可用 → 添加超时和降级处理，检索失败时正常回答（不阻塞）

## Open Questions

1. 是否需要支持多知识库空间的联合检索？（首期仅支持单空间）
2. 引用详情页面是跳转新页面还是弹窗展示？（首期使用弹窗）
3. 是否需要展示检索过程的透明度（如"正在检索知识库..."）？（建议首期支持）
